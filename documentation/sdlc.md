# Skills across the SDLC

I use the [common seven-phase breakdown](https://www.ibm.com/think/topics/sdlc): **planning, requirements analysis, design, implementation, testing, deployment and maintenance**. Other models group the phases differently. Discovery identifies what is worth building; feedback checks whether the delivered product helped and informs the next cycle. Both can happen during development. The boundaries in the diagram describe scope, without requiring sequential handoffs.

![Project foundations, discovery, seven-phase SDLC cycle, product feedback and skills across the lifecycle](images/sdlc-cycle.svg)

Change assessment and completion evidence connect these phases: `project-conventions` preserves the application context, and `deliver-reliable-changes` distinguishes implementation, verified behavior, deployment readiness and post-deployment verification. The depth follows the changed risk.

Use the [task menu and phase examples](usage.md#skills-you-invoke) to start work. `develop` spans the useful lifecycle from a rough idea; focused tasks let you enter at any phase. User/automation invocation is distinct from supporting skill selection.

Choose the skills that help with the current task. Research, clarification and writing support every phase. Project foundations sit outside the repeating cycle and change as the application evolves.

Project foundations sit outside the repeating cycle: establish structure, stack constraints, instructions, local setup and delivery capabilities for a new project, then maintain the affected parts as it evolves. The entry arrow into Planning is not a required setup gate for every change. CI/CD is a maintained capability used during implementation, testing and deployment.

Across discovery, development and feedback: [humanizer](https://github.com/blader/humanizer/blob/225a6f39ac85f76ee48dbad772ea4abe4ed6c9d8/SKILL.md) edits prose in every phase, preserving meaning, commands and factual caveats. [research](https://github.com/mattpocock/skills/tree/4588b32ecab9ecc9fc8cc6b6c5e7d675b6004b0d/skills/engineering/research) and [grill-me](https://github.com/mattpocock/skills/tree/4588b32ecab9ecc9fc8cc6b6c5e7d675b6004b0d/skills/productivity/grill-me) can support any relevant phase. `grill-me` still starts only on an explicit request; placing it here does not authorize automatic interrogation. [documentation-conventions](../plugins/development-workflow/skills/documentation-conventions/SKILL.md) keeps project knowledge aligned; [git-contributions](../plugins/development-workflow/skills/git-contributions/SKILL.md) supplies the default worktree/commit/PR flow; [security-and-privacy-design](../plugins/development-workflow/skills/security-and-privacy-design/SKILL.md) revisits data and authority risks. Trail of Bits skills support specific security and dependency reviews; they do not cover every security or privacy concern. Capacity, cost and recovery constraints inform design as well as maintenance. CI/CD supports implementation and testing as well as deployment.

The wider catalogue includes helpers and stack tools for more specific tasks. See the [upstream catalogue](maintainer-reference.md#upstream-catalogue) and [workflow selection](../plugins/development-workflow/WORKFLOW.md) for the wider inventory. Tickets remain optional.

## Reliability across phases

`reliability-design` follows the user outcome from requirements into design, acceptance and operation. `observability-operations` implements and checks the signal contract as code and topology evolve. Neither is confined to maintenance. Runbooks support deployment and response; incident learning feeds the next requirements/design iteration, separate from product feedback about value.

The cycle image shows representative entry points; the table and [usage guide](usage.md) carry the wider inventory. Kubernetes resource guidance applies only to Kubernetes; JVM tuning applies only to JVM workloads. Datadog/Terraform monitoring is an optional implementation example.

## Performance and controlled failure testing

[performance-testing](../plugins/development-workflow/skills/performance-testing/SKILL.md) provides k6 guidance for local development, an application started on a CI runner, and a deployed non-production target. It connects design/capacity assumptions to testing and deployment verification; runner results do not establish production capacity.

[resilience-testing](../plugins/development-workflow/skills/resilience-testing/SKILL.md) defines hypothesis, failure scope, observation, stop conditions, cleanup and independent recovery. Start with relevant fixtures or isolated tests; deployed faults require the established target/action policy. Load and faults answer different questions and can be combined only for an intended scoped experiment. Platform-specific mechanisms and application acceptance targets remain contextual.

Compatibility, validated configuration, trustworthy test suites, supported-version upgrades and deliberate retirement connect design, implementation, testing, deployment and maintenance through the existing backend/project/delivery skills.

For meaningful frontend design, interaction-design defines behavior and inventories all affected surfaces before code, then verifies coverage. Backend conventions similarly establish contracts, invariants, authority and state transitions first. Review and documentation span phases; task selection does not require sequential stage gates.


## Implementation feedback and local evidence

Use the [evaluation loop](usage.md#evaluate-during-implementation) during meaningful increments, not only in a final testing phase. Acceptance and interaction/contracts guide component, journey, visual/accessibility and exploratory evaluation; observed failures return to implementation or design. Versioned AI cases and appropriate live experiments cover model quality separately from deterministic application handling. Repeated unexplained failures and missing execution remain explicit blockers.

Project foundations provide an isolated Compose environment for containerizable services and optional telemetry. Portable OTel instrumentation connects local and deployed evidence without requiring the same backend. Platform-native clients and device checks retain their actual host requirements. Diagnostics support evaluation; they do not independently establish correctness or production readiness.
