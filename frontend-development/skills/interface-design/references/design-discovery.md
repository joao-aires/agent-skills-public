# Design Discovery and a durable brief

Read when a consequential product or visual direction remains open. Reuse the existing brief, design system and prior user feedback first. Discovery belongs to the activity already requested; it does not authorize a redesign during a critique.

## Choose how much participation helps

| Context | Response |
| --- | --- |
| Small repair or established product screen | Inspect existing tokens, components and behavior; ask only about a consequential unresolved choice. |
| New product or substantial redesign | Propose two or three distinct directions on realistic content, recommend one, and invite feedback before costly propagation. |
| User says “use your judgment” or work is unattended | Choose a reversible direction, record assumptions as proposed/delegated, build one representative slice and keep progressing. |

Understand the primary task, audience, actual content, platform, brand commitments and constraints before aesthetic exploration. Product category informs the recommendation without determining taste. A finance tool can be expressive; an exercise tracker can be quiet.

Show alternatives with the same content and viewport so the choice concerns direction rather than feature differences. Prefer a small rendered concept or existing permitted visual reference when tools allow it. Label sketches and external references accurately; do not present an image search result as a proposed implementation. Explain what each direction improves and costs: density versus breathing room, character versus familiarity, motion versus attention and device cost.

Ask one concise round about the highest-impact unknowns. For example: “I recommend the quiet, compact version for daily analysis. Would you prefer that, a warmer spacious version, or a more expressive presentation?” Follow up only when the answer changes implementation materially. Translate “more modern” into a visible change to composition, type or interaction, then show it. Avoid asking users to choose technical token values. Color intensity, light/dark policy, density, typography personality, imagery, motion and information priority are useful dimensions, not a mandatory form.

Keep one feedback owner. When using bundled methods, supply the known brief and resolve only their genuinely missing context; avoid independent questionnaires or conflicting design-system files. Explain preference conflicts with accessibility or primary task completion and offer a feasible alternative. Do not turn an upstream style warning into an absolute ban that overrides an explicit brief.

## Persist decisions where the project already keeps them

Update the existing design/product record; if absent and implementation is authorized, use `documentation/design/brief.md` (adapt to project conventions). A design-only engagement may return the brief as its artifact. Never overwrite an unrelated `DESIGN.md` or duplicate an adequate record. Keep the brief short enough for the next agent to use:

```markdown
# Interface brief
- Scope and primary user task:
- Audience, content and important states:
- Existing commitments / allowed changes:
- References and what they contribute (including asset rights):
- Direction: proposed / accepted by user / delegated; decision source and date:
- Visual rules: hierarchy, density, typography, color, imagery, shared tokens:
- Interaction and motion intent; reduced-motion/static equivalent:
- Implementation mapping and device/browser constraints:
- Acceptance evidence: routes/states/viewports, accessibility and performance budget:
- Open questions / assumptions:
- Feedback and revision: what changed, why, affected surfaces, superseded decisions:
```

Distinguish observed product evidence, agent proposals and user decisions. Read this record at resumption; ask again only when new evidence or a changed scope invalidates an earlier choice. UI/UX Pro Max's optional persisted output is supporting candidate material until reviewed for product fit. Link it from the brief if retained; it does not silently become the authority.

After the first representative implementation, show the actual result and invite focused feedback: “Is the information density right for the task?” or “Should the movement be calmer?” Incorporate replies while continuing independent work. Record the change and propagate it through shared owners. No response is not approval; report the implemented assumption and evidence, without making every screen a permission gate.
