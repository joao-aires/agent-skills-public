# Turn project cases into worked learning

Use this reference when study chapters, comparisons or a learning library are requested. Project guides own how a product works; study material explains concepts, alternatives and decisions across cases. Neither a reading list nor an assignment alone teaches the subject.

## Keep the organization intelligible

In an existing library, preserve its useful structure and canonical owners. For a new multidisciplinary library, a small entry point, dimensions/classification pages, project folders, study folders and a research-method reference can suffice. Repository maintenance guidance belongs in its existing docs/instructions. Do not create every possible subject folder before content exists.

Organize study through complementary responsibilities:

| Lens | What belongs here |
| --- | --- |
| Organizational disciplines | Strategy/leadership, product management, design, engineering, marketing/growth, support and finance/company operations. |
| Engineering foundations | Shared reasoning about architecture, state, code/contracts, testing, delivery and operations. |
| Engineering specialties | Deeper responsibilities such as frontend, backend, databases, data engineering, AI, security and reliability/platform. |
| Application expertise | Task/domain meaning: objects, authority, workflows, information architecture and outcomes. |
| Technical expertise | Compatible language/framework/database/platform APIs, implementation idioms and executable checks. |

AI engineering is a specialty that applies shared product, architecture, quality and operating concerns to AI systems. A particular inference/evaluation SDK is technical expertise. Voice dictation is an application problem; macOS is a platform. A role route can combine these without putting them in the same taxonomy or copying their content into another role folder.

Keep the connection between project assessments and study explicit. The assessment asks how a product realizes a concern; the chapter teaches how to reason about that concern. Website/acquisition design retains its own teaching home even when product design and engineering share the same subject vocabulary.

When a library-wide view helps orientation, use an editable diagram connecting classifications and assessment dimensions to project guides, then project cases to study subjects and role routes. An SVG can serve as a compact entry-point map. Label relationships as relationships; the picture must not imply a compulsory workflow or become another maintained project registry.

## Supply the work before asking for practice

Choose a bounded decision and observable objective. State the reader's prerequisites, supply sufficient starting inputs and label synthetic assumptions/results. Define concepts through the situation before using them in complex analysis. Work through intermediate reasoning to a finished artifact, compare a credible alternative, then show a plausible failure and its consequence.

For example, a synthetic authoring tool has saved version 7, unsaved draft 8 and a passing execution of version 7. Introduce saved state, draft and execution identity. The completed explanation says that the old success cannot validate the new draft; the interface preserves those identities separately. Compare requiring save-before-run with retaining an immutable unsaved run snapshot. Both can work under explicit product constraints.

Now practice: ask the learner to interpret an old result, complete a save-conflict decision, design a new workflow independently, then transfer the reasoning to another task such as dictation. Supply hints and explained answers, including acceptable alternatives. For the interpretation task above, an answer must preserve “draft 8 unsaved; last execution used version 7”; one green status would hide the distinction. This feedback is more useful than “a good answer considers tradeoffs.”

Match artifacts to the discipline. A strategy chapter can supply positioning alternatives and an investment/stop decision. A design lesson can work through objects, navigation, feedback and a website narrative. Finance can show denominators and sensitivity under supplied costs. Engineering can trace state and failures. Code is useful only when the learning objective requires it.

[CMU's learning-objective guidance](https://www.cmu.edu/teaching/designteach/design/learningobjectives.html), consulted 5 November 2026, informs alignment between observable objectives, instruction and assessment. Following that guidance does not establish measured learning effectiveness.

## Use project cases and comparisons carefully

Use a specific project mechanism to illustrate a concept, link its owning explanation and explain the transfer limit. Compare cases on the same question. A bookmark extension and a browser automation graph may share message APIs while needing different task structures. A native utility and an agent dashboard may both need cancellation identity without sharing navigation.

Reusable patterns need applicability, the preserved invariant, costs, a counterexample and the condition that changes the choice. A proposed architecture decision records context, alternatives, choice, consequences and a revisit trigger. Do not attribute that proposal to the source company or turn one project's threshold into a universal standard.

For a cross-discipline capstone, supply the brief and a worked reference solution: product promise, requirements, journey/states, architecture/data/authority, verification, useful-progress signals and cost/operating decision. Explain how those artifacts agree. An exercise list without the resulting solution remains a proposed assignment.

## Keep depth and future reuse honest

Use overview for orientation, explained chapter for worked reasoning/practice, and guided lab for an executable procedure with prerequisites and expected observations. Record actual execution separately, including versions, inputs, failures and unexecuted boundaries. A paper answer is legitimate teaching material; it is not an experiment, benchmark, customer validation or independent learner study.

Check arithmetic and code/command compatibility where they support conclusions. A local framework fixture cannot establish native input or hosted-provider quality. Reader-question review can be by the author; call independent testing only when another reader actually participated under a recorded scope.

When later skill derivation is requested, use the transferable decision, conditions, example/counterexample and completion evidence rather than copying a chapter. Reinspect the destination's current ownership; distinguish general methods, application meaning and selected-stack mechanisms. Extraction, evaluation of candidate guidance and public contribution are separate requested activities, not automatic outputs of every analysis.
