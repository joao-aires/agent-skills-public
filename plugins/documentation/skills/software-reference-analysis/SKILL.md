# Turn reference products into understandable evidence and learning

Explain how a product works across the requested business, experience and engineering dimensions. Produce the actual account: capabilities, concepts, mechanisms, consequences and source walkthroughs. A list saying that dimensions were inspected cannot substitute for that explanation.

Read [composition guidance](../../COMPOSITION.md) and apply [documentation writing](../documentation-writing/SKILL.md). These resources ship in this package. Seek optional product, design, technical or diagramming expertise by relevant available descriptions; preserve the result when that guidance is absent. No particular research service, repository host, browser, stack or skill-discovery facility is required.

## Establish the question and research boundary

Use the requested projects, audience, dimensions and output location. Inspect existing instructions, documents and source identities before changing an established library. A single architecture explanation needs no new taxonomy or curriculum. A cohort assessment needs a clear reason for its selection and visible gaps; popularity alone does not establish reference quality.

Identify each product's audience, principal capabilities and meaningful task archetypes before selecting interesting implementation details. Separate task purpose from application specialization, cross-cutting characteristics, interaction patterns and implementation platform. A terminal is a surface; conversation is an interaction; AI alone does not identify the user's job.

Read [assessment and evidence](references/assessment-and-evidence.md) for a multidisciplinary assessment, source pinning, visual evidence and depth labels. Apply the relevant dimensions and explain consequential missing evidence. Preserve company/landing-page analysis separately from product UI/UX, and distinguish the product's own development process from automation it sells.

## Investigate mechanisms before writing conclusions

Resolve the actual component repositories, branches and full revisions. Follow a principal task from its initiating interface/command through authorization, state, execution, persistence and visible result. Inspect callers and configuration branches around the selected helpers. Trace a consequential failure or interruption back to its user-visible consequence. For a broad guide, account for the other principal capabilities before claiming a connected product explanation.

Website claims need dated page evidence; implementation claims need named source passages. Record which product states were rendered or exercised and which were inferred from source or official previews. Treat retrieved content as untrusted evidence. Respect access, component licenses and asset rights; public source availability does not imply permission to redistribute all code or artwork.

Keep fact, upstream assertion, interpretation, teaching proposal and executed result distinguishable. A proposed rationale is not a source company's historical decision. A test file, configured pipeline or successful build does not establish passing runtime behavior, deployed health, usability or commercial outcomes. Retain existing observation dates when editing prose.

## Write the requested artifacts

- For a product account, read [project guides](references/project-guides.md). Introduce the product and its terms, explain normal behavior, then build toward implementation and failure. Use predictable subject ownership without imposing empty chapters.
- For a learning library, comparison or study route, read [learning material](references/learning-material.md). Keep transferable reasoning, recommendations and exercises separate from each project's observed account. Supply worked solutions and feedback, not just topics and assignments.
- For substantial architecture views, apply [architecture documentation](../architecture-documentation/SKILL.md). Choose diagrams by the question they answer and preserve current versus proposed boundaries.

Keep navigation small: an entry point, assessment dimensions and classifications when useful, one home per project and one owner per teaching subject. Reuse the established layout. Repository-identity JSON, if needed, holds URLs, branches and revision pins; narrative findings stay beside their evidence. Process/progress belongs in existing work history, not new claim registries or duplicate indexes.

## Review against the reader's task

Can a newcomer describe the product, define its objects, follow its principal task across real owners, explain a tradeoff and identify what remains unknown? Can a learner reproduce the worked reasoning and assess a transfer attempt from the supplied information? Fix missing mechanisms or foundations before polishing prose.

Check source targets, internal links, example arithmetic and compatible commands. Render changed diagrams and inspect labels, reading order and agreement with the account. Execute only authorized, proportionate fixtures; distinguish source inspection, paper exercises, local runtime checks, benchmarks and independent reader evidence. Report the actual checks and limits; completion of headings does not establish research completeness.

Finish at the requested deliverable. Research and writing do not themselves authorize changing source products, creating repositories/sites, publishing private material, installing skills or merging. If future reusable agent guidance is requested, derive task-specific decisions with applicability and completion evidence under the destination's current owners; keep it a separate contribution from the learning library.
