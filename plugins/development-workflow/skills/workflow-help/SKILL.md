# Workflow help

Read [task guidance](../../TASKS.md). Use its task catalogue and the client's observed skill/plugin inventory when available. Explain what to use for the user's current phase/outcome, give one or two copyable examples and state expected results/side effects. If the stopping point is unclear, distinguish product direction, a design/plan, implementation or assessment. Recommend installed product-management for an unresolved product problem and develop when working software is requested. Reuse accepted context for a defined feature or defect.

Distinguish installed/observed skills and tools from this package's catalogue and optional bundles; do not claim a tracker, MCP, browser or credential is available without evidence. Explain plugin-qualified commands where the client supports them, otherwise plain-language invocation; do not invent a universal alias or shell flag parser. The client's built-in help is separate. Cover explicit user/automation starts versus supporting guidance, interactive questions versus unattended blockers, and the current action policy. Help is read-only: do not run setup, probes, tests, installs, create schedules or begin the suggested activity. Link the usage/SDLC guides through their published URLs when useful.

Choose the user-facing activity first, explain its expected result, then name only the methods and stack guidance that matter. Product management, visual design and backend design can also be requested directly when installed; a selectable discipline is not an instruction to start a full lifecycle. Recommend the next activity without firing explicit-only skills, probing accounts or beginning work. Preserve the difference between catalogue entries and observed availability.
